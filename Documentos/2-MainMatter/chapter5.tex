\chapter{Results and Evaluation}
\label{cha:discussion}

This chapter evaluates the computational performance, scalability limits, and runtime feasibility of the proposed model-driven \gls{DT} framework. The central premise of this work is that industrial simulation environments can be assembled and executed procedurally from standardized, vendor-neutral \gls{AAS} packages without relying on hard-coded scenes or static configuration files.

To assess whether this procedural approach remains viable under realistic and high-density manufacturing conditions, a comprehensive empirical stress test was conducted. The evaluation measures how the Unity 3D physics runtime and the semantic ingestion pipeline behave across varying asset scales, tracking startup parsing latencies, rendering fluidity (\gls{FPS}), frame time percentiles, and unit computational costs.

The remainder of this chapter is organized as follows:
\begin{itemize}
    \item \Cref{sec:eval_methodology} defines the experimental benchmark methodology, testing environment, hardware specifications, and workload scale levels.
    \item \Cref{sec:eval_startup_complexity} analyzes the startup initialization time, package parsing latency, and algorithmic complexity of procedural scene generation.
    \item \Cref{sec:eval_fluidity_fps} evaluates rendering fluidity and frame rate degradation across module scales, comparing steady-state averages against 1\% low frame drops.
    \item \Cref{sec:eval_frametime_latency} examines frame render latency, jitter, tail latency percentiles (P95 and P99), and unit computational costs per conveyor module.
    \item \Cref{sec:eval_timeseries_stability} presents dynamic time-series evolutions over 60-second test runs and provides statistical correlation analyses across all recorded performance variables.
    \item \Cref{sec:eval_discussion} discusses the practical boundaries of real-time physics engines, identified bottlenecks, and architectural trade-offs.
\end{itemize}

\section{Experimental Methodology and Testbed Configuration}
\label{sec:eval_methodology}

The experimental evaluation was designed to stress-test the procedural scene generation pipeline and the real-time simulation engine under controlled, repeatable conditions. Rather than benchmarking a single fixed production layout, the system was subjected to workload scaling across eight discrete module density levels:
\begin{equation*}
    N \in \{5,\, 10,\, 25,\, 50,\, 100,\, 250,\, 500,\, 1000\} \text{ conveyor modules}.
\end{equation*}

Each conveyor module represents a complete modular asset encapsulated in an official \gls{AAS} archive (AASX format). Each package contains the low-polygon visual mesh (GLB format), the kinematic degrees of freedom, the surface-anchored virtual sensor and actuator pins, the behavioral rule engine logic, and the associated technical metadata.

For each scale level $N$, an automated test harness conducted 100 independent experimental runs, totaling 800 full simulation lifecycles. In each run, the simulation executed the following standardized pipeline:
\begin{enumerate}
    \item \textbf{Package Ingestion and Parsing:} The Unity runtime accessed the designated asset packages, unpacked the internal XML and JSON submodels, extracted the embedded 3D GLB binary files, and reconstructed the visual mesh hierarchies in memory.
    \item \textbf{Kinematic and Physics Rigging:} Rigidbodies, box colliders, kinematic joints, and physics surface materials were attached procedurally to each conveyor link and belt surface.
    \item \textbf{Simulation Execution:} Once procedural assembly completed, the physics simulation started. Dynamic workpieces were spawned and transported across the conveyor modules according to active belt velocities.
    \item \textbf{High-Frequency Metrics Logging:} A background monitoring thread recorded frame rate (\gls{FPS}) and frame time (milliseconds) at 500\,ms intervals over a 60-second steady-state duration.
\end{enumerate}

All benchmark tests were executed on a Lenovo laptop equipped with a 13th Generation Intel Core i7-13650HX processor (14 cores, 20 threads up to 4.9\,GHz), 16\,GB of DDR5 RAM, and an NVIDIA GeForce RTX 4060 Laptop \gls{GPU} with 8\,GB of VRAM, running Windows 11 Home (version 25H2) and Unity 6 (version 6000.3.10f1).

\section{Startup Initialization and Procedural Instantiation Complexity}
\label{sec:eval_startup_complexity}

A critical measure of usability in model-driven engineering is the time required for the virtual runtime to discover, parse, and instantiate an arbitrary factory line. \Cref{fig:eval_startup_boxplot} depicts the distribution of startup initialization times across all 100 runs per scale level, while \Cref{fig:eval_startup_complexity} displays the scaling trend alongside the unit instantiation cost per module.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.88\linewidth,height=0.40\textheight,keepaspectratio]{5-Figures/eval_startup_time_boxplot.pdf}
    \caption{Startup initialization time distribution across module scales (5 to 1000 conveyor modules).}
    \label{fig:eval_startup_boxplot}
\end{figure}

The empirical results show that for realistic production line scales (between 5 and 50 conveyors), the procedural generation process is nearly instantaneous. Initializing a cell of 5 conveyors required an average of $2.61\,$s ($\sigma = 0.10\,$s), while a 50-conveyor installation initialized in $5.22\,$s ($\sigma = 0.09\,$s). Scaling to a facility of 100 conveyors took $8.55\,$s ($\sigma = 0.11\,$s), and a large 250-conveyor layout was assembled in $20.60\,$s ($\sigma = 0.40\,$s).

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.88\linewidth,height=0.40\textheight,keepaspectratio]{5-Figures/eval_startup_complexity.pdf}
    \caption{Procedural scaling complexity: total startup initialization time versus unit instantiation cost per conveyor module.}
    \label{fig:eval_startup_complexity}
\end{figure}

As shown in \Cref{fig:eval_startup_complexity}, the unit startup time per conveyor module exhibits an initial downward curve, dropping from 522.0\,ms/module at $N=5$ to 104.4\,ms/module at $N=50$, and reaching a minimum of 82.4\,ms/module at $N=250$. This behavior demonstrates that the fixed overhead of starting the runtime engine, initializing rendering shaders, and preparing disk I/O buffers is quickly amortized across larger asset populations.

However, beyond $N=500$, initialization time increases non-linearly, reaching $57.45\,$s at 500 modules and $416.70\,$s at 1000 modules. This escalation is driven by the main-thread bottleneck of Unity's mesh collider generation and the sequential file decompression of multiple AASX zip archives.

\section{Rendering Fluidity and Frame Rate Degradation}
\label{sec:eval_fluidity_fps}

To evaluate visual responsiveness and stability, \Cref{fig:eval_fps_degradation} illustrates the degradation of mean frame rate alongside the 1\% low frame rate metric (which highlights severe transient frame drops) relative to the industrial 60\,FPS target (16.6\,ms) and the 30\,FPS critical threshold (33.3\,ms).

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.88\linewidth,height=0.42\textheight,keepaspectratio]{5-Figures/eval_fps_degradation.pdf}
    \caption{Rendering fluidity and frame rate degradation across conveyor module counts, showing mean steady-state FPS, standard deviation, and 1\% low FPS.}
    \label{fig:eval_fps_degradation}
\end{figure}

For layouts up to 250 conveyor modules, the procedural \gls{DT} operates with substantial performance headroom. The mean frame rate reaches $460.80\,$FPS for 5 conveyors, $344.68\,$FPS for 50 conveyors, and $254.24\,$FPS for 250 conveyors. Crucially, the 1\% low frame rate remains above $98.4\,$FPS across these scales, confirming that the simulation runs smoothly without stuttering or visual hitching during workpiece transitions.

At $N=500$ modules, the mean frame rate drops to $93.16\,$FPS ($\sigma = 20.98\,$FPS). While this average comfortably exceeds the 60\,FPS threshold, the 1\% low metric decreases to $38.4\,$FPS. This dip occurs when dozens of moving pallets simultaneously engage belt friction colliders, triggering bursts of narrow-phase collision calculations.

At $N=1000$ modules, the system experiences severe bottlenecking, averaging $13.96\,$FPS ($\sigma = 43.28\,$FPS) with 1\% low values approaching zero. At this scale, the single-threaded PhysX physics update saturates the CPU, exceeding the real-time threshold and proving that unconstrained 1000-module facilities require spatial culling or multi-threaded physics sub-stepping.

\section{Frame Render Latency, Tail Latency, and Computational Cost}
\label{sec:eval_frametime_latency}

Real-time synchronization between physical automation hardware and a virtual twin requires consistent and bounded frame execution times. \Cref{fig:eval_frametime_percentiles} displays the scaling of mean frame latency against the 95th (P95) and 99th (P99) tail latency percentiles. \Cref{fig:eval_unit_frame_cost} presents the unit computational cost required to process each conveyor module per frame.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.88\linewidth,height=0.40\textheight,keepaspectratio]{5-Figures/eval_frametime_percentiles.pdf}
    \caption{Frame render latency and tail percentiles (P95 and P99) as a function of active conveyor count.}
    \label{fig:eval_frametime_percentiles}
\end{figure}

The latency benchmarks show that from 5 to 100 conveyor modules, mean frame times remain well below 4\,ms: $2.49\,$ms at $N=5$, $3.30\,$ms at $N=50$, and $3.73\,$ms at $N=100$. Tail latencies are similarly well-controlled, with the P99 latency reaching only $4.8\,$ms at 100 modules and $8.2\,$ms at 250 modules, safely within the 16.7\,ms frame budget.

At $N=500$, the mean frame time rises to $14.96\,$ms, while the P99 tail latency reaches $34.2\,$ms.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.88\linewidth,height=0.40\textheight,keepaspectratio]{5-Figures/eval_unit_frame_cost.pdf}
    \caption{Unit computational processing cost per conveyor module in microseconds ($\mu$s/conveyor).}
    \label{fig:eval_unit_frame_cost}
\end{figure}

As shown in \Cref{fig:eval_unit_frame_cost}, the unit computational cost per conveyor module reveals an inverse scaling efficiency at moderate counts. Processing an individual conveyor requires approximately 498\,$\mu$s at $N=5$, decreasing to 66\,$\mu$s at $N=50$, and reaching an optimal minimum of 21.7\,$\mu$s at $N=250$. At $N=1000$, inter-collider matrix checks cause unit costs to rise sharply to 342.2\,$\mu$s per module.

The Pearson correlation matrix in \Cref{fig:eval_correlation_matrix} provides quantitative confirmation of key architectural behaviors:
\begin{itemize}
    \item \textbf{Conveyor Count vs.\ Frame Time ($r = 0.84$):} Computational frame latency correlates strongly with module count, demonstrating direct dependency on physics scene complexity.
    \item \textbf{Frame Time vs.\ Startup Time ($r = 0.99$):} Demonstrates that the processing overhead of mesh collider creation during startup directly mirrors the ongoing cost of narrow-phase collision checks during simulation.
    \item \textbf{Mean FPS vs.\ 1\% Low FPS ($r = 0.92$):} Confirms that frame drops remain tightly coupled to the underlying average performance rather than being triggered by anomalous background spikes.
\end{itemize}

\section{Discussion and Limitations}
\label{sec:eval_discussion}

The experimental results validate that the proposed model-driven framework can procedurally generate and execute industrial \gls{DT} simulations from standardized \gls{AAS} packages without pre-compiled scenes. However, several practical constraints and performance boundaries were identified:

\begin{enumerate}
    \item \textbf{Single-Threaded Physics Bottleneck ($N > 500$):} Unity's default PhysX engine updates rigid-body dynamics sequentially on the main CPU thread. While the framework scales comfortably up to 250 modules (averaging over 250\,FPS) and maintains real-time execution at 500 modules (93\,FPS), performance drops to 14\,FPS at 1000 modules. For facilities exceeding 500 active conveyors, future work should implement spatial culling or migrate rigid-body dynamics to compute shaders using Unity's Data-Oriented Technology Stack (DOTS).
    \item \textbf{Package Ingestion I/O Overhead:} At large scales, opening and extracting hundreds of separate AASX zip archives introduces significant disk I/O overhead during startup ($416\,$s at 1000 modules). Implementing an in-memory package cache or pre-indexing submodel manifests could substantially reduce initialization times for large-scale production facilities.
    \item \textbf{Geometric Optimization Trade-Offs:} The fast loading times and low resource overhead observed in the benchmarks rely on the low-polygon geometric models generated in Layer~0. While these simplified meshes represent kinematic envelopes and sensor triggers accurately, they omit internal manufacturing details.
\end{enumerate}

In summary, the evaluation demonstrates that the framework provides responsive, bounded real-time performance for modular production lines containing up to 250 modules, while maintaining valid operational fidelity up to 500 modules, confirming the feasibility of model-driven digital twin generation in smart manufacturing.
